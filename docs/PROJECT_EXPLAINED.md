# SupplySync AI Project Explained

This is the interview and viva guide for the current repository. It explains what the project does, where each important behavior lives, and how to demo it without pretending the system is bigger than it is.

## 1. Problem Statement

SupplySync AI is an inventory decision support system. Given a SKU, recent demand, current stock, lead time, service level, MOQ, order multiple, and optional budget limit, it forecasts near-term demand and recommends whether to reorder.

Business problem: small inventory teams need to avoid both stockouts and overstock. A raw forecast is not enough; the user needs a practical order quantity that respects purchasing constraints.

Technical problem: the app must connect data ingestion, forecasting, inventory math, persistence, and a usable dashboard without hiding where each value came from.

AI problem: demand is not uniform. Some SKUs have regular demand, some are intermittent, and some have very sparse sales. The system must choose a forecasting method that fits the observed demand pattern.

## 2. Complete User Flow

1. The user opens the dashboard.
2. The frontend calls `/health`, `/api/kpis`, `/api/skus/details`, and `/api/analyses/recent`.
3. The dashboard shows model/data readiness, backtest KPIs, SKU recommendations, stock controls, provenance badges, and recent analyses.
4. The user searches or selects a SKU.
5. The SKU detail page loads `/api/skus/{sku}/history`, `/api/stock/{sku}`, and posts to `/api/analyze`.
6. The backend resolves demand history, classifies the SKU, runs the chosen forecasting path, computes the reorder decision, persists analysis and prediction audit rows, then returns the same response shape expected by the UI.
7. The UI displays P50/P90 demand, risk, safety stock, reorder point, recommended quantity, explanation text, and method provenance.

## 3. Frontend Pages

- `frontend/app/page.tsx`: main dashboard with system status, pipeline, KPI cards, risk tabs, searchable SKU table, stock editing, and recent analyses.
- `frontend/app/sku/[id]/page.tsx`: SKU workspace with history chart, planning controls, recommendation summary, forecast details, and inventory decision fields.
- `frontend/app/layout.tsx`: app shell metadata and global styling.
- `frontend/components/DataSourceBadge.tsx`: shared provenance badge for model, statistical, rule-based, request, historical, synthetic, server, demo, and local fallback sources.

## 4. Important Frontend Controls

- Search filters the SKU table.
- Risk tabs filter recommendations by risk level.
- Current stock inputs let the user override demo defaults and re-run analysis.
- Lead-time and service-level controls on the SKU page change planning assumptions.
- SKU table rows navigate to the detailed SKU workspace.
- Recent analyses show persisted backend analysis history.

## 5. Graphs And KPIs

Dashboard KPI cards come from `/api/kpis` and summarize the project backtest. The SKU detail chart shows recorded historical demand when the SKU exists in the processed dataset. The horizontal reference lines are historical demand summary levels: the backend field named p50 is currently the historical mean used for risk classification, while p90 is the historical 90th percentile.

Key metrics:

- WAPE: weighted absolute percentage error, useful for total forecast error relative to total demand.
- MAE: average absolute error.
- RMSE: penalizes larger misses.
- MASE: compares a model against a naive baseline.
- Stockout and holding-cost style KPIs: generated by the inventory policy simulation scripts.

## 6. API Routes

Auth and health:

- `GET /health`: backend, model, data, KPI, database, and artifact readiness.
- `GET /api/auth/status`: tells the frontend whether demo auth is required.
- `POST /api/auth/login`, `POST /api/auth/logout`, `GET /api/auth/me`: demo-grade auth flow.

Dashboard and SKU data:

- `GET /api/kpis`: cached backtest KPIs.
- `GET /api/model-info`: model metadata and evaluation summary.
- `GET /api/skus`: top SKU IDs.
- `GET /api/skus/details`: dashboard SKU rows.
- `GET /api/skus/{sku}/history`: recorded daily demand history.
- `GET /api/analyses/recent`: persisted recent analysis runs.

Stock:

- `GET /api/stock`: latest stock values.
- `GET /api/stock/{sku_id}`: latest stock for one SKU.
- `PUT /api/stock/{sku_id}`: save a stock update.

Decision endpoint:

- `POST /api/analyze`: demand resolution, forecasting, inventory decision, explanation, persistence, and prediction logging.

- `services/analysis_service.py`: orchestration for `/api/analyze`.
- `services/intelligent_inventory_service.py`: combines forecasting and inventory decision logic.
- `services/adaptive_forecasting_service.py`: demand classification and method routing.
- `services/model_routing_service.py`: uses evaluation evidence when available.
- `services/stock_service.py`: stock validation and persistence use cases.

## 8. Repository And Database Architecture

Routes do not call SQLAlchemy directly. The flow is:

```text
FastAPI route
  -> service
  -> repository
  -> SQLAlchemy session
  -> database
```

Repositories:

- `analysis_repository.py`: `analysis_runs` and `prediction_logs`.
- `stock_repository.py`: SKUs and latest stock snapshots.
- `forecast_evaluation_repository.py`: evaluation evidence.
- `model_artifact_repository.py`: model artifact lifecycle rows.

## 9. Data Pipeline

The project uses UCI Online Retail II. Ingestion scripts clean transaction data into a daily SKU demand table. The trained model and KPI/evaluation artifacts are generated by backend scripts and then consumed by the API at runtime.

Important artifacts:

- `data/raw/online_retail_II.csv`: raw source dataset, user-provided.
- `data/processed/daily_demand.parquet`: processed demo demand table.
- `backend/data/cached_kpis.json`: dashboard KPI cache.
- `backend/data/forecast_evaluation.json`: offline model comparison evidence.
- `backend/saved_models/`: LightGBM model and metadata.

## 10. Demand Classification

Demand classification is based on the share of zero-demand days. Regular SKUs go to the ML path when possible. Intermittent SKUs go to Croston SBA. Highly intermittent SKUs use a conservative buffer. If the ML path cannot run, the system uses a simple-average fallback.

## 11. LightGBM

LightGBM is the trained ML model path for regular demand. It uses lag and calendar-style features built from demand history. The model artifact is loaded from disk and validated with metadata before serving predictions.

Why use it: tree-based gradient boosting can model nonlinear relationships from engineered features and is a realistic baseline for tabular demand forecasting.

Tradeoff: it is only credible when the SKU has enough regular historical signal and the feature schema matches the trained artifact.

## 12. Croston SBA

Croston SBA is used for intermittent demand. It separately estimates demand size and demand intervals, then applies the SBA correction to reduce Croston's upward bias.

Why use it: intermittent demand has many zeros, so ordinary averages or ML point forecasts can be misleading.

Tradeoff: it is still a simple statistical method and does not learn product-level covariates.

## 13. Conservative Forecast

Highly intermittent demand uses a conservative rule-based buffer. This is intentional: when very few days have non-zero demand, point forecasts can look precise while being fragile.

Why use it: better to be honest and conservative than to overstate ML confidence on sparse data.

## 14. Simple-Average Fallback

The simple-average path is a fallback when the normal ML path is unavailable, usually because the model artifact is missing or feature construction cannot produce a valid row.

Why use it: the API can still provide a transparent approximate answer instead of failing silently.

## 15. Why Each Method Is Used

- Regular demand: LightGBM, because there is enough signal for feature-based ML.
- Intermittent demand: Croston SBA, because zero-heavy demand needs a sparse-demand method.
- Highly intermittent demand: conservative rule, because the data is too sparse for confident point modeling.
- ML unavailable: simple average, because it is transparent and easy to explain.

## 16. Alternatives And Tradeoffs

Possible alternatives include ARIMA, Prophet, XGBoost, CatBoost, DeepAR, Temporal Fusion Transformers, and probabilistic forecasting. The current project intentionally stays with LightGBM plus classical sparse-demand methods because it is understandable, testable, and appropriate for a student-scale monolith.

## 17. Model Routing

Routing combines demand-class logic with evaluation evidence when available. The system exposes the executed `forecast_method`, `forecast_source`, and `routing_reason` so the frontend can show why a recommendation was produced.

## 18. WAPE And Evaluation Evidence

Offline evaluation compares LightGBM against baselines. In this repo's intermittent-demand evaluation, Croston SBA beats LightGBM for sparse demand, which is why the project should not claim LightGBM is always superior.

WAPE is important because it measures absolute error relative to total demand. For inventory, aggregate miss size often matters more than percentage error on individual low-volume days.

## 19. Safety Stock Formula

The standard idea is:

```text
safety_stock = z_score(service_level) * demand_uncertainty * sqrt(lead_time_days)
```

The exact implementation lives in `backend/src/inventory/reorder_point.py` and related inventory service code.

## 20. Reorder Point Formula

```text
reorder_point = lead_time_demand + safety_stock
```

If current stock is below the reorder point, the system recommends ordering enough to recover the position while respecting business constraints.

## 21. Business Constraints

The decision layer accounts for:

- MOQ: minimum order quantity.
- Order multiple: round to valid purchasing increments.
- Max order quantity: cap unusually large recommendations.
- Budget: constrain recommendation when a unit cost and budget are supplied.

## 22. Prediction Logging

Every successful analysis can create a `prediction_logs` row with SKU, timestamp, demand source, forecast method, model name/version, input history length, forecast horizon, P50/P90 output, daily forecast, recommended quantity, and nullable actual observed demand.

This makes later forecast monitoring possible without changing the user-facing response.

## 23. Forecast Evaluation

`forecast_evaluations` stores evidence from offline evaluation and logged-prediction evaluation. Offline evaluation supports routing decisions before enough live predictions mature. Logged evaluation can later compare predicted demand against observed demand windows.

## 24. Model Artifacts

Model metadata includes model name, version, checksum, feature schema version, and lifecycle status. The backend validates artifact metadata at startup so a wrong or stale model is detected early.

## 25. Database Tables

- `skus`: canonical SKU rows.
- `stock_levels`: stock snapshots per SKU.
- `inventory_policies`: reorder assumptions per SKU.
- `analysis_runs`: one persisted decision response summary.
- `prediction_logs`: forecast audit rows linked to analyses.
- `forecast_evaluations`: model/method evaluation evidence.
- `model_artifacts`: artifact lifecycle metadata.

Relationships:

- One SKU has many stock levels.
- One SKU has many analysis runs.
- One analysis run can have linked prediction logs.
- Evaluation rows may link to prediction logs when they evaluate a logged forecast.

## 26. Alembic

Alembic manages database schema changes. Local PostgreSQL setup should run:

```powershell
cd backend
$env:DATABASE_URL="postgresql+psycopg2://supplysync:supplysync@localhost:5432/supplysync"
python -m alembic upgrade head
```

SQLite is still useful for tests and lightweight local fallback, but PostgreSQL is the deployment-oriented target.

## 27. Health And Configuration

Configuration comes from environment variables and `backend/src/config/settings.py`. `/health` reports model, data, KPI, database, and model-artifact readiness. Invalid critical settings should fail early instead of producing misleading runtime behavior.

## 28. Authentication Limitations

Auth is intentionally demo-grade. `AUTH_MODE=off` keeps local demos simple. `AUTH_MODE=demo` enables a shared credential and HMAC session cookie. This is not a production identity system with users, organizations, password reset, or RBAC.

## 29. Deployment Flow

At deployment time:

1. Provision a PostgreSQL database.
2. Set `DATABASE_URL`, `ALLOWED_ORIGINS`, and any auth variables.
3. Install backend dependencies.
4. Run Alembic migrations.
5. Ensure required model/data/KPI artifacts are available.
6. Start FastAPI.
7. Deploy the Next.js frontend with `NEXT_PUBLIC_API_URL` pointing to the backend.

## 30. Testing

Backend tests cover forecasting, inventory decisions, API behavior, settings validation, persistence, routing evidence, model artifacts, and stock services. Frontend validation uses TypeScript and linting.

Run:

```powershell
cd backend
python -m pytest tests -q

cd ..\frontend
npm.cmd test
npm.cmd run build
```

## 31. Honest Limitations

- Dataset is public historical retail data, not live company inventory.
- Auth is demo-grade.
- No organization/user multi-tenancy.
- No purchase order workflow.
- No background job queue for mature production monitoring.
- Unknown SKUs use synthetic demo demand.
- Logged prediction evaluation depends on actual demand becoming available later.

## 32. Future Scope

Best next improvements:

- Clearer deployment checklist for non-Docker local machines.
- More logged-prediction evaluation examples once windows mature.
- Better admin workflow for model promotion.
- Production-grade auth only if the app needs real users.
- Monitoring and structured logs after deployment basics are stable.

## 34. 30-Second Pitch

SupplySync AI is a FastAPI and Next.js inventory decision system built on UCI Online Retail II. It classifies SKU demand, routes regular demand to LightGBM and intermittent demand to Croston-style methods, then converts forecasts into reorder recommendations using safety stock, reorder point, MOQ, order multiple, and budget constraints. It also logs predictions and persists analysis history through SQLAlchemy so the recommendations are auditable.

## 35. 2-Minute Explanation

The project starts with retail transaction data and converts it into daily demand per SKU. The backend exposes a dashboard API and an `/api/analyze` endpoint. When a SKU is analyzed, the service resolves demand history, labels the source as historical, request-provided, or synthetic, classifies the demand pattern, chooses a forecasting method, and computes historical demand summary values for risk classification. Then the inventory logic calculates safety stock, lead-time demand, reorder point, risk, and recommended order quantity while respecting business constraints.

The frontend shows this as a dashboard and SKU workspace. It keeps provenance visible so users can tell whether a recommendation came from the trained LightGBM model, Croston SBA, a conservative statistical path, or a rule-based fallback. Persistence is handled through SQLAlchemy repositories for stock, analyses, prediction logs, evaluations, and model artifacts.

## 36. 5-Minute Technical Explanation

SupplySync is a clean monolith. The frontend is a Next.js app with a dashboard and per-SKU workspace. It calls typed client functions in `frontend/lib/api.ts`, formats machine identifiers in `frontend/lib/utils.ts`, and renders provenance in `DataSourceBadge.tsx`.

The backend is FastAPI. `main.py` owns route contracts and dependency wiring, while the core `/api/analyze` workflow lives in `AnalysisService`. That service coordinates `DataService`, `IntelligentInventoryService`, repositories, and prediction logging. Forecasting is adaptive: regular demand uses LightGBM when available, intermittent demand uses Croston SBA, highly intermittent demand uses a conservative buffer, and simple average is a transparent fallback. Inventory math then converts forecasts into reorder decisions.

Persistence follows route to service to repository to SQLAlchemy session. Alembic manages schema migrations. Tables include SKUs, stock snapshots, inventory policies, analysis runs, prediction logs, forecast evaluations, and model artifacts. This gives the project traceability: the UI can show recent analyses, and future monitoring can compare predictions with actual observed demand.

The ML story is intentionally honest. Offline evaluation exists, WAPE is reported, and the system does not claim LightGBM is best when intermittent-demand evidence favors Croston SBA. Model artifacts have metadata, versioning, checksums, and lifecycle status so predictions can be traced to the artifact that produced them.
